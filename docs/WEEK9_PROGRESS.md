# Week 9 Progress: Selenium UI Testing

## Objective

Add browser-based automated tests for the highest-value Child Education
Sponsorship System workflows while leaving the Spring Boot application,
controllers, templates, and Week 8 deployment pipeline unchanged.

## Selenium Test Plan

The Selenium suite exercises the rendered Thymeleaf UI in headless Chrome:

1. `landingPageLoadsWithExpectedTitleAndMainContent` checks the landing page
   title, main heading, and sponsorship navigation link.
2. `sponsorshipListAndDashboardNavigationWorks` navigates from the landing page
   to sponsorship records, opens the dashboard, and returns to the list.
3. `createSponsorshipThroughForm` uses the actual form and verifies the new
   record appears in the records table.
4. `searchFindsAutomationRecord` creates a test record, searches by its child
   ID, and verifies the matching record appears.
5. `statusWorkflowUpdatesAutomationRecord` creates a test record, changes its
   status through the row's status form, and verifies the updated status.

The tests use explicit waits and selectors grounded in the existing HTML:
field IDs generated by Thymeleaf `th:field`, the records search input's
`name="search"`, the status select's `name="status"`, and existing link and
button attributes. Browser options enable headless mode for future CI use.

## Selenium Scripts and Setup

The JUnit 5 class is
`src/test/java/com/prerna/sponsorship/selenium/SponsorshipUiIT.java`. Selenium
4 is declared as a test-scoped Maven dependency. ChromeDriver is created with
Selenium Manager; there is no separately downloaded or hard-coded driver path.

The test base URL defaults to `http://localhost:8001` and can be overridden with
`-Dui.base-url=<url>`. Each data-dependent test generates a unique
`AUTO-SEL-<UUID>` child ID, creates the record using the UI, and removes only
that matching record in `@AfterEach`. No manually-created records are required
or deleted. The application uses an in-memory H2 database; Selenium runs
against the live application instance and its current database.

## Local Execution

Start the application in a separate terminal from the repository root:

```powershell
mvn spring-boot:run
```

Wait for startup to complete, then run the Selenium suite from another terminal:

```powershell
mvn failsafe:integration-test failsafe:verify
```

To run only the create flow:

```powershell
mvn "-Dit.test=SponsorshipUiIT#createSponsorshipThroughForm" failsafe:integration-test failsafe:verify
```

The standard `mvn test` continues to run the existing JUnit integration tests;
Failsafe discovers the `*IT` browser test separately. No Jenkins Selenium stage
is claimed here; connecting this suite to Jenkins is planned for Week 10.

## Test Report and Results

Final verified Selenium result: 5 tests run, 5 passed, 0 failures, 0 errors,
0 skipped. The focused `createSponsorshipThroughForm` run passed: 1 test, 0
failures, 0 errors. Chrome and Selenium Manager successfully started headless

## Failure and Defect Evidence

The initial create-flow run submitted the browser's actual values and received
HTTP 400 at `/sponsorships/save`, rather than the controller's expected redirect
to `/sponsorships`. The captured controls showed:

- `age=120` instead of 12 because the number input began at 0 and the test
  appended digits.
- `sponsorshipAmount=125500.0` instead of 125.50 because the number input began
  at 0.0 and the test appended digits.
- `startDate=60929-02-20` instead of the intended ISO date because Chrome's
  localized native date input did not interpret the typed ISO digits as
  expected.

The test-only fix clears both number inputs before typing and sets the date
input's ISO value through Selenium's JavaScript executor, dispatching input and
change events. No application behavior or templates were modified. The focused
create test and full five-test suite passed after this correction.

## Known Limitations and Week 10

- A browser must be installed on the machine executing the tests. Selenium
  Manager resolves the matching ChromeDriver; the first run may require network
  access to download it.
- The app must already be running at the configured base URL. It is not started
  or stopped by the Selenium test class.
- Tests use the application's in-memory H2 database; records do not persist
  after the application restarts.
- One preceding full-suite rerun observed a transient
  `StaleElementReferenceException` in the status-update check after navigation;
  the subsequent full Failsafe run passed all five tests. Recheck this flow
  during Week 10 Jenkins integration.
- Jenkins Selenium integration is not implemented or verified in Week 9. Week
  10 must provide a Windows agent with Chrome available, start the app before
  Failsafe runs, and execute the Failsafe goals after deployment while keeping
  Jenkins on port 8000 and the app on port 8001.
